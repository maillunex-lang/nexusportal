# NEXUS Project Blueprint 1.0

Универсальный детерминированный модуль: JSON от внешнего архитектора → проверка → предпросмотр diff → явное утверждение → безопасная выдача задач → технические свидетельства → приёмка директором. Платных AI API нет. Метаданные и названия проверок никогда не исполняются.

## Запуск из свежего main

Текущий main на момент реализации содержит только проектную документацию и tools/work_plan.py. Поэтому добавлен самостоятельный FastAPI-модуль, без слияния feat/nexusportal-full-v1 или PR #2. Python 3.12+, SQLite WAL, FastAPI, нативный HTML/CSS/JS. Node-сборка не нужна.

```bash
python -m venv .venv
. .venv/bin/activate
pip install -r backend/blueprint/requirements.txt
python -m backend.blueprint.app --init-owner
python -m backend.blueprint.app --db blueprint.sqlite --local-http
```

Первый шаг создаёт новый файл blueprint-users.json с scrypt-хешем, правами 0600, через интерактивный ввод. Существующий файл не перезаписывается. Секреты не передаются аргументами команд. Открыть http://127.0.0.1:8765/blueprint, имя owner. --local-http используется только для loopback-разработки; при HTTPS убрать этот флаг. Самостоятельный процесс слушает только loopback. Для реального развёртывания использовать HTTPS reverse proxy и один ASGI worker (сессии и limiter находятся в памяти, при перезапуске потребуется вход). Этот PR ничего не развёртывает.

## Работа директора

1. Архитектор читает утверждённые GDD/roadmap и готовит JSON по schemas/project-blueprint-1.0.json. Образец: project_blueprint.example.json; ещё три проекта: examples/blueprint/.
2. «Blueprint проекта»: загрузить JSON до 1 MiB, проверить, посмотреть структуру и diff. Импорт не означает утверждение.
3. Утвердить версию. Если изменены принятые задачи или их зависимости/документы, подтвердить перечисленный сброс. Активные изменения требуют отдельного подтверждения; активную задачу нельзя удалить до её отмены. Все старые документы, PR, тесты и решения сохраняются.
4. «Что делать сейчас»: выбрать одну параллельную группу. Остальные группы — альтернативы с пересекающимися зонами, а не разрешение запускать всё сразу.
5. В карточке прочитать исходный промпт, GDD и критерии. Директор подтверждает смысл и ограничения заметкой, при необходимости уточняет зоны (по строке на путь). JSON остаётся неизменным; уточнения хранятся в состоянии.
6. «Скопировать промпт для ChatGPT / Claude»: атомарно закрепляет задачу, сохраняет выданный текст и переводит в in_progress. Повторное копирование возвращает сохранённый текст. Если clipboard недоступен, текст выделяется для ручного копирования.
7. Заполнить исполнителя, PR, тесты и статусы. После tests_passed директор явно выбирает accepted с причиной. Только это открывает зависимости. «Готово», зелёный CI или merged не означают accepted.
8. При изменении GDD импортировать новую версию, проверить diff и последствия, утвердить. Если другая версия утверждена после импорта, повторно импортировать файл: устаревший draft не может заменить актуальный план.

## Контракт и очереди

Схема Draft 2020-12, schema_version строго 1.0; основные поля обязательны, типы строгие. Дополнительные метаданные допускаются, но не влияют на авторизацию, статусы или выполнение. Встроенное в JSON поле status игнорируется. ID задач и этапов уникальны, каждая задача входит ровно в один этап, зависимости существуют и образуют DAG. Предел: 500 задач, JSON-вложенность 32 уровня.

file_scopes=[] допустим. Такая задача получает отдельную эксклюзивную группу и не стартует при других активных задачах. До записи исполнитель обязан изучить репозиторий и согласовать зоны. Можно сразу подтвердить реальные зоны в карточке. Подтверждённые зоны имеют приоритет над исходными зонами плана.

Проверка пересечений консервативна: непересекающиеся буквальные префиксы разрешают параллельность; общие/неизвестные/неоднозначные wildcard-префиксы сериализуются. Общая рабочая ветка также сериализуется. parallel_group — метаданные архитектора, не разрешение обходить конфликты. Зависимые задачи сортируются по доступности, затем priority по убыванию, при равенстве — ID. Этапы отображают прогресс; порядок выдачи задаётся зависимостями, а не именами каталогов или этапов.

todo → ready/in_progress/blocked/cancelled; in_progress → pr_open/tests_passed/failed/blocked/cancelled; pr_open → in_progress/tests_passed/failed/blocked/cancelled; tests_passed → accepted/in_progress/pr_open/failed/blocked/cancelled; blocked/failed/cancelled → todo (и blocked/failed → cancelled). accepted терминален до явного пересмотра Blueprint. Возврат todo снимает подтверждение промпта.

Промпт архитектора сохраняется побайтно как строка и добавляется после служебного контекста. Типовые опасные указания блокируются правилами; понимание произвольного естественного языка без AI API не гарантируется, поэтому подтверждение смысловой проверки директором обязательно. Конфликтующее исходное задание исправляется новой версией, обхода через «игнорировать конфликт» нет.

## Встраивание в полную версию портала

После отдельной интеграции feat/nexusportal-full-v1, до регистрации SPA catch-all в create_app:

```python
from backend.blueprint.portal_adapter import attach
attach(app, db_path='/path/to/blueprint.sqlite', github=portal.github)
```

Передать реальный существующий GitHubClient из контейнера зависимостей портала (имя portal.github в примере следует сверить при интеграции). Новый отдельный SQLite-файл исключает вмешательство в чужие миграции. Авторизация и CSRF используют существующий require_owner; отдельные Blueprint login/session являются адаптером к существующей auth. В существующую навигацию добавить ссылку /blueprint. В main этих компонентов ещё нет; чужая ветка не изменяется и не сливается.

Для иных хостов: install(app, Store(path), authorize, github), где authorize — FastAPI dependency, проверяющая сессию/CSRF и возвращающая actor/role. owner: импорт/утверждение/проверка/приёмка; executor: выдача, статусы, PR/тесты; viewer: чтение. Самостоятельный режим поддерживает те же роли в серверном users-файле.

GitHub-интеграция только читает PR, актуальный head SHA, checks/statuses, merged и файлы. ReadOnlyGitHub переиспользует существующий клиент; список файлов пагинируется до лимита GitHub, при возможном усечении синхронизация отклоняется. До/после чтения сверяется SHA. Форки и чужие ветки отклоняются. Принятие и статусы автоматически не меняются. Если GitHub недоступен, ручной режим продолжает работать. Сохранённые проверки не равнозначны required-check policy: их оценивает директор. base SHA в выдаваемом промпте берётся только из живого branch_sha, никогда из JSON.

## API

Все операции требуют сессию; записи дополнительно X-CSRF-Token и роль. Базовый путь /api/blueprint.

| Метод / путь | Действие |
|---|---|
| POST /import | Сырой JSON, валидация и draft |
| GET /versions, /versions/{id} | История, полный документ и diff |
| POST /versions/{id}/approve | expected_version, reset_ids, ack_active |
| GET /projects/{id} | Документ, состояние и объяснённая очередь |
| GET /projects/{id}/history | Неизменяемый журнал решений |
| POST /projects/{id}/tasks/{task}/review | version, note, scopes |
| GET /projects/{id}/tasks/{task}/prompt?version=N | Предпросмотр, без выдачи |
| POST /projects/{id}/tasks/{task}/dispatch | Атомарная выдача, version |
| POST /projects/{id}/tasks/{task}/status | version, expected_status, status, note, executor, pr, evidence |
| POST /projects/{id}/tasks/{task}/github | version, read-only GitHub sync |

Изменения выполняются через BEGIN IMMEDIATE; проверка актуальной версии и статуса внутри транзакции защищает от гонок и устаревших вкладок. Документы, приёмки, выданные промпты и аудит защищены append-only SQL-триггерами. Миграция аддитивна/идемпотентна, незнакомая более новая версия БД отклоняется. Не является защитой от администратора SQLite с правом менять саму схему.

Запрещены абсолютные, traversal, Windows/URL-encoded пути, небезопасные ветки и рабочая ветка, равная базовой. Файлы из Blueprint не читаются и не исполняются. UI использует textContent, CSP запрещает inline scripts. Модуль не выполняет shell, merge, deploy или удаления данных.
