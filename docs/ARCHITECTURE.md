## Решения, принятые при реализации (без отдельного согласования)

| ID | Решение | Почему |
|---|---|---|
| IMP-01 | Владелец создаётся только CLI-командой `set-owner`, веб-регистрации нет | исключает захват свежей установки |
| IMP-02 | Пароль — scrypt; сессия — случайный токен в HttpOnly/Secure/SameSite=Strict cookie, в БД только SHA-256 | утечка БД не даёт сессий |
| IMP-03 | CSRF — токен сессии в заголовке `X-CSRF-Token` для всех изменяющих запросов | SameSite + токен |
| IMP-04 | Ограничение входа: 5 неудачных попыток за 5 минут с IP | перебор паролей |
| IMP-05 | Секреты только в файлах 0600, запись через UI/CLI, чтение никогда не возвращается; журналы фильтруются | NP-17 |
| IMP-06 | Webhook отвечает сразу, обработка в фоне; дубликаты по `X-GitHub-Delivery` отбрасываются; ошибки сохраняются | таймаут GitHub 10 с |
| IMP-07 | Обязательные проверки = явно заданные в проекте ∪ required checks защиты ветки; пустой список блокирует слияние | NP-18 «явно заданные и непустые» |
| IMP-08 | Слияние squash с параметром `sha`; SHA берётся из свежего ответа API в момент решения | гонки пушей |
| IMP-09 | PR привязывается к задаче по ветке задачи или `[ID]` в названии | детерминированно |
| IMP-10 | `done` выставляет только код после `merged: true` или проверенного webhook о слиянии; вручную и из файла — нельзя | NP-13 |
| IMP-11 | Мастер пишет файлы в ветку `nexus/bootstrap-*` и открывает PR; создание без `sha` — GitHub сам отклонит перезапись | NP-09 |
| IMP-12 | Сценарии деплоя хранятся в портале (версия + sha256), служба только `nexus-<slug>-*.service`, пути только `/srv/nexus/<slug>` | «не трогать другие службы» |
| IMP-13 | Хранится текущий + 2 предыдущих релиза деплоя и 5 версий загрузок; 10 архивов резервных копий | откат |
| IMP-14 | Релиз: `release.json` + `SHA256SUMS` + файл; канал `release`; имя без debug/test/unsigned; APK с подписью v1/v2+, не «Android Debug»; при наличии `apksigner` — полная проверка | NP-25 |
| IMP-15 | Автопубликация релизов и prod-деплой включаются владельцем отдельно в каждом проекте (по умолчанию выключены) | «без продакшена без разрешения» |
| IMP-16 | Резервная сверка — один asyncio-цикл раз в 15 минут, без отдельных воркеров | лёгкие фоновые процессы |
| IMP-17 | MAX: `POST {NEXUS_MAX_API}/messages?chat_id=` с заголовком `Authorization`; адрес настраивается | API MAX может меняться |
| IMP-18 | Маршрутизация интерфейса через hash (`#/tasks`), без внешнего роутера | минимум зависимостей, работа PWA офлайн |
| IMP-19 | Мониторинг CPU/RAM/диска не реализуется | NP-30 |

## Безопасность критических операций

- слияние: аварийные выключатели, разрешение проекта, не форк, задача, required checks на актуальном SHA, mergeable, `sha` в запросе;
- деплой: prod только с разрешением, автоматический — с учётом выключателей, ключ хоста проверяется, команды экранируются;
- релиз: не форк, событие push/release/dispatch, SHA = голова основной ветки, контрольная сумма, подпись;
- журнал действий `audit_log` для входов, настроек, слияний, деплоев, релизов (с маскированием секретов).

## NEXUS Smart Context

| ID | Решение |
|---|---|
| SC-01 | Движок `backend/context/engine.py` только на stdlib; копируется в проекты как `tools/context_pack.py` |
| SC-02 | Модули задачи: явное поле `modules` в work_plan.json, иначе вывод по пересечению `file_scope` с каталогами модулей |

| SC-06 | В CI этого репозитория `context_pack.py check --strict` и проверка актуальности PROJECT_INDEX.md |

## NEXUS Project Blueprint

Модули: `backend/blueprint/core.py` (стандарт, проверка, очерёдность, параллелизм, задания; только stdlib, копируется в
проекты как `tools/blueprint.py`), `backend/blueprint/service.py` (версии, утверждение, «Что делать сейчас», история),
`backend/api/blueprint.py`, экраны `Now.tsx` и `Blueprint.tsx`. Стандарт — `docs/blueprint/`.

| ID | Решение |
|---|---|
| BP-01 | Формат `nexus-blueprint/1`: документ описывает **замысел** (этапы, потоки, задачи, промпты), состояние ведёт портал. Поле `status` в задачах игнорируется с предупреждением |
| BP-02 | Портал не создаёт задач и не требует структуры папок; `scope_hints` — только подсказки и сигнал конфликта |
| BP-03 | Безопасный параллелизм: общий `resources`, пара `conflicts_with`, один `workstream` (если `parallel_within_workstream: false`), пересечение `scope_hints`, лимит `max_parallel` |
| BP-04 | Порядок: топологическая сортировка; ключ — этап, приоритет P0–P3, длина критического пути, позиция в документе (детерминированно) |
| BP-05 | Версии: импорт создаёт черновик (повтор того же sha256 — та же версия), утверждение заменяет предыдущую (`superseded`); diff по ID задач и полям |
| BP-06 | При утверждении задачи синхронизируются в существующую дорожную карту портала — автослияние, CI, PR, память работают без изменений; прогресс и `done` сохраняются по ID |
| BP-07 | Удаление задач в работе (`in_progress`/`blocked`) требует явного принудительного утверждения |
| BP-08 | `conventions.required_checks` добавляются к обязательным проверкам проекта при утверждении |
| BP-09 | Задание = шапка портала (проект, ветка, PR) + промпт архитектора без изменений + критерии, проверки, правила; варианты вступления для Claude, ChatGPT, Codex и прочих; для заблокированной задачи добавляется промпт исправления CI |
| BP-10 | История задач — таблица `blueprint_events` (добавлена/изменена/удалена, PR открыт/обновлён, CI упал, слита, задание скопировано) |
| BP-11 | План Adaptive Project Engine (PR #2) импортируется конвертером `from_adaptive`; файлы PR #2 не изменялись |
| BP-12 | JSON Schema (draft 2020-12) — официальный формат; в портале — эквивалентная проверка на stdlib плюс ссылочная целостность и циклы (их Schema не выражает); соответствие проверяется тестами с `jsonschema` |
