# NEXUS Adaptive Project Engine · Режимы 1 и 2 (MVP)

**Статус:** автономное Python-ядро в отдельной ветке, без платных AI API. Веб-интерфейс и интеграция с текущим NEXUS PORTAL пока НЕ подключены. Данные примера не относятся к реальному игровому репозиторию.

## Режим 1: детерминированный планировщик
- Читает проектный JSON, который должен быть составлен на основе актуального GDD и инвентаризации репозитория.
- Проверяет уникальность задач, зависимости, циклы, зоны файлов, статусы и критерии приёмки.
- Предлагает параллельные пакеты задач и показывает блокировки.
- Не выдаёт зависимые задачи до статуса **accepted**. `tests_passed` и `pr_open` недостаточно.
- Консервативно блокирует задачи при пересечении файловых зон с уже выполняемой работой.
- Никаких фоновых агентов, платных API, SSH, удаления данных и автоматических слияний.

## Режим 2: промпт для исполнителя
- Для доступной задачи собирает готовый русский промпт с GDD, веткой, SHA (только если указан в плане), файловой зоной, критериями приёмки, проверками и отчётностью.
- Если SHA не указан, требует получить свежий SHA, а не придумывает его.
- Запрещает выдачу задачи с неизвестной зоной файлов, неготовыми зависимостями или конфликтом с активной задачей.
- Промпт можно скопировать в ChatGPT, Claude, Codex или отправить разработчику вручную. Подписка на чат **не равна** доступу к API.
- Автоматическая отправка исполнителям не реализована.

## Использование
```bash
python tools/adaptive_project.py validate docs/adaptive_project/example_plan.json
python tools/adaptive_project.py next docs/adaptive_project/example_plan.json
python tools/adaptive_project.py prompt docs/adaptive_project/example_plan.json --task A1
python -m unittest discover -s tests -p 'test_adaptive_project.py' -v
```

## Подключение реального проекта
1. Прочитать GDD и правила проекта, зафиксировать версию/хеш документов.
2. Инвентаризировать реальные файлы, тесты и команды сборки, **не предполагая** общих путей.
3. Составить `project_plan.json` с задачами, зонами файлов, зависимостями и критериями приёмки.
4. Проверить граф и согласовать план. Только после этого выдавать промпты.
5. Получать результаты GitHub PR/CI через отдельный адаптер и требовать явного принятия директором перед разблокировкой зависимых задач.
6. При изменении GDD или структуры репозитория пересматривать затронутые задачи и зоны, не запускать старые промпты автоматически.

## Ограничения первой версии
Нет автоматического парсинга произвольного GDD, индексатора репозиториев, синхронизации PR/CI, состояния в базе, UI, мониторинга и отправки задач в Claude/ChatGPT. Проверка конфликтов по путям эвристическая и не выявляет все контрактные зависимости. Не заявлять, что движок уже полностью автономен.
